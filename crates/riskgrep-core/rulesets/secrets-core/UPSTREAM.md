## Translation

- Each rule becomes one YARA-X rule named after the gitleaks id with `-` replaced by `_` (and `_` prepended to an id starting with a digit).
- Regexes are read with Go (RE2) syntax: a `{` that does not start a repetition is escaped for Rust and YARA-X; nothing else changes.
- The regex is the anchor `$re`, with lazy quantifiers rewritten as greedy (YARA-X refuses mixed greediness). The original regex is kept as `span_regex`; the `span` post-processor re-runs it inside each match to find the secret: `secretGroup` when the rule sets it, otherwise as gitleaks does, the first capture group that matched non-empty, else the whole match (`secret_group = "first_nonempty"`; `secret_group = 1` when group 1 always takes part and is never empty, which selects the same text).
- In `$re` only, a repetition of 4 or more over a class of at most 11 characters with no letters (`[0-9]{11}`, `\d{15,16}`) is written `(?:RUN|$^)`. YARA-X otherwise searches for every 4-digit string in place of the rule's literal prefix, which made digit-dense text scan as slowly as 0.8 MB/s. Without multi-line mode `$^` matches only an empty input and no converted regex matches the empty string, so `$re` matches exactly what it did. A regex that sets multi-line mode (an inline flag group containing `m`) is not rewritten, because `$^` also matches between lines there; the rule is listed under Not translated.
- The `span` post-processor reports every non-overlapping match of `span_regex` inside each `$re` match, so a match that runs over several secrets yields one location per secret.
- `line_complete = true` is set when every match of `span_regex` stays on the line of its secret. When the secret is one capture group (`secret_group` 1 or more) inside a top-level element of the regex, nothing up to the end of that element may match a line feed, and the rest of the regex either cannot match one or is one element whose every alternative that can is at most one byte long, such as gitleaks' trailing delimiter `(?:[\x60'"\s;]|\\[nr]|$)`. Otherwise (`secret_group = 0` or `"first_nonempty"`) no part of `span_regex` may match a line feed. Any literal or class that admits one counts, including `\s`, `\W`, `\D`, negated classes, `[\s\S]`, dot-all `.`, `[[:space:]]`, and `\n` or `\x0a`. A line feed can then only be the last byte of a match, which belongs to the line it ends; the search for the next match resumes at the start of the following line, and since nothing before a secret can match a line feed, no later match needs that byte. With one location per secret (above), the locations cover every secret, each on one line, and the Claude Code hook offers partial reads only for files whose findings all come from such rules. 111 of the 222 rules are marked; `cargo test -p riskgrep-core --test ruleset_secrets every_line_complete_rule_locates_every_secret` checks each of them with generated secrets on one line, on adjacent lines, with CRLF line endings, and at the end of a file without a final line feed.
- Keywords are `nocase` literals `$kw0..n`; the rule needs one of them and `$re`.
- `entropy` becomes the `entropy` post-processor on the secret. gitleaks drops a secret whose entropy is at most the threshold; the post-processor drops one below it.
- Allowlist stopwords become `stopwords/secrets_core_<rule>.txt` (rule and global stopwords) or `stopwords/secrets_core_global.txt` (global only).
- Allowlist regexes that target the secret become one `allow_regex` alternation (rule and global regexes).
- Allowlist paths become `not path matches` conditions; the global ones are the private rule `gitleaks_global_path_allowlist`.
- A rule `path` becomes a `path matches` condition; a rule with only a path yields one evidence item.
- A regex that would match its own rule text has its last literal letter or digit wrapped in a one-character class (`abc` becomes `ab[c]`), in both `$re` and `span_regex`. It matches the same secrets, and the shipped ruleset does not report itself.
